## 1. 概述

**DoraHub 是跨设备持久化 agent 驾驶舱**：会话状态住在常开的云 VM（pi-durable + SQLite），任何设备用浏览器接入同一个 agent 现场——完整历史、实时流式、随时插话、远程放行。工具执行路由到用户自己的电脑（执行机），不是云沙箱。

核心洞察：**在电脑前，用户要的是"现场感"——亲眼看着 agent 干活、随时插话或叫停；离开电脑，会话不丢，回来接着看**。与 sig（管家：你不在场它替你调度）构成同一底座上的两种产品形态，见参考分析 §0。

一句话对照：**sig 的用户说"帮我办了"；DoraHub 的用户说"让我看着你办"**。

## 2. 目标用户与使用场景

**目标用户**：已在用 pi（及同类 coding agent）的开发者。当前 single-player（站长本人，三设备）；近期 = 邀请制小团队（≤3 人共享一个 hub）；远期 = 开源 self-hosted（每团队一实例）。永不做多租户 SaaS。

典型场景（按频率排序）：

1. **日常驾驶**：在 workpc 开着侧栏，选中会话，发任务，看流式输出，中途 steer 改方向，确认卡放行
2. **离开再回来**：合上电脑出门；手机/另一台设备打开 hub，同一个会话还在跑，现场同步
3. **等你处理**：多个会话并行跑，某个停下来要确认——从「◆ 等你 N」一眼看到，跳过去放行
4. **收工看汇报**：一轮跑完，末尾收尾卡给出 tone/结论/工具统计/耗时，不用翻全量消息
5. **接着昨天的活**：从侧栏项目分组找到昨天的会话（或 pi 会话导入），上下文都在，直接续
6. **跨机接力**：活儿在 laptop 上跑了一半，机器要关——执行机切换 + 工作区迁移，换 workpc 继续
7. **导入已有 pi 会话**：在终端里聊了一半的 pi 会话，导入 hub 变成持久会话，获得多设备能力

**第一分钟体验**（对齐 sig 的旅程定义，我们 10-29 才补上）：打开 → 零会话时「从这两步开始」（新建会话选执行机 / 导入已有 pi 会话）→ 首条消息发出 → 流式回复出现（60 秒内第一次正反馈）→ 自动命名/分组出现。

## 3. 设计原则

1. **设备是窗口，会话是家**：任何设备接入同一现场，永不需要交接文档。一切的持久化、实时同步、断线恢复都服务这一条
2. **现场感优先**：流式输出、工具调用、确认请求实时可见；人随时能插话（steer）或叫停（abort）
3. **值得信任的持久**：崩溃不是损失而是暂停，断点续跑是产品承诺；无人看时现场也不丢（幽灵流）
4. **工具在用户的电脑上跑**：执行路由到真实工作区（注册的执行机），操作真实文件，不是云沙箱玩具
5. **状态由系统推导，不让人维护**：三态（等你处理/运行中/空闲）、unread、等你徽章全部服务端派生，用户永远不手动"标记已读/切换状态"
6. **安静但可追溯**：不打扰（无推送轰炸），但每件事可下钻——收尾卡 → 消息流 → 原始事件

差异化坚守：多执行机远程执行、pi 会话管理（导入/搬运）、自托管轻部署、自写渲染（markdown/diff/确认卡，无 UI 组件库）。

## 4. 核心概念

| 概念 | 定义 |
|---|---|
| **会话（Conversation）** | 用户心智里的「一个 agent 现场」= 一台执行机上一个 cwd 里的一段持久对话。有名字/描述/关键词（自动生成，可改），按项目分组 |
| **执行机（Executor）** | 用户的一台电脑（hub/workpc/laptop），SSH 出站连接，在线探测，会话指定它执行工具 |
| **工作区（cwd）** | 会话的工作目录，执行机上的真实路径；跨机迁移搬运的是它 |
| **确认卡（Confirmation）** | agent 请求放行危险操作的卡片（guard 规则触发），等待/批准/拒绝三态，10 分钟超时 fail-closed |
| **收尾汇报卡（Run report）** | 每轮 run 结束时确定性生成的总结卡（tone 徽章/结论行/工具统计/耗时），不调 LLM |
| **pi 会话** | 终端里 pi CLI 产生的历史会话（.jsonl），可扫描/导入为 durable 会话/跨机搬运 |
| **迁移（Transfer）** | 会话工作区跨执行机搬运：harvest 文件清单 → 中转 → 校准提示 |
| **等你处理（Needs you）** | 服务端派生态：有未处理的确认卡。聚合入口在侧栏 header（桌面）+ 列表页 header（手机） |

## 5. 会话与状态模型

### 5.1 状态单位

用户视角的单位是**会话**（不是 Thread）：一个会话 = 一个现场。跨机迁移后的会话仍是同一个（这正是「会话是家」的体现）；fork 是新会话（带 parent 历史）。

pi 导入的会话与原生会话**无差别**：导入后就是 durable 会话，具备全部能力。导入是迁移手段，不是二等类型。

### 5.2 三态派生模型（P0-1，2026-10-28 上线）

会话在列表里按**派生状态**分三区，全部服务端推导，**永不手动设置**：

| 状态 | 判定依据 |
|---|---|
| **◆ 等你处理** | 有 pending 确认卡（pendingConfirms > 0） |
| **▶ 运行中** | status = running |
| **项目分组（空闲）** | 其余，按项目（cwd 推导）分组，组内按最近活动排序 |

**unread 标志**：会话产生了用户没看过的 assistant 输出（有人 attach 观看时不算），列表蓝点 + read 帧清除（进入会话页即读）。

**没有显式「已完成」状态**。完成是一个事件（收尾卡），不是会话状态——系统不替用户宣布「这事结束了」。旧会话按时间自然下沉，随时可以追加指令让它复活。

### 5.3 上下文接力

同一会话天然共享全部上下文（pi-durable 持久层），这是与 sig 的 relay 模型的根本差异：**我们不需要 handoff brief，因为现场从未中断**。跨机迁移时工作区文件随行 + 校准提示（让 agent 重新感知环境差异）；fork 时继承 parent 历史。

已知成本：上下文只增不删，长会话 eventual compaction 是 roadmap 项。

## 6. 人的参与方式（自主性边界）

按「出错的代价」划线（对齐 sig §6 的框架，我们的版本）：

| 层级 | 内容 |
|---|---|
| **agent 自主，不打扰** | 读文件/搜索/分析；写操作在已放行的 cwd 内；retry 类 |
| **必须等人（确认卡）** | guard 规则定义的危险操作（git push/删文件/装包…，guard-rules.json 可配）；超时 fail-closed（默认拒绝） |
| **人主动介入** | steer（运行中插话，排队到下一轮生效）、abort（中止当前 run）、fork（从当前点岔开）、/model 切渠道 |

关键规则：**确认卡是单一出口**——所有工具放行请求都走 askConfirmation（10-28 修复 guardCb 绕过直广播的 bug 后成立）。等待中的确认卡在「等你处理」聚合可见，不因刷新/换设备丢失（mount 补拉 + attention 广播帧）。

## 7. 交互与界面

### 7.1 信息架构（2026-10-18 定型，硬约束）

- **桌面（≥769px）两栏**：左栏常驻（header：品牌/◆等你/⚙/＋新建 + 会话列表三区 + pi 会话区），右侧会话页/空态
- **手机（<769px）驾驶舱**：单栏；列表页 header 有「◆等你」入口（P0-4，只读聚合+跳转，是驾驶舱克制原则的显式例外）；会话页 header `[←] 标题 [⋯]`（切模型/中止/分叉在菜单）；**无设置齿轮**
- 设置弹窗三页签（执行机/渠道与模型/关于）——只在桌面

### 7.2 可见性分层（从粗到细）

列表卡（三态/未读点/等你徽章/关键词）→ 收尾汇报卡（一轮的结论）→ 消息流（markdown/diff/工具卡）→ 原始事件（WS 帧）。用户 90% 的注意力只在前两层。

### 7.3 状态的诚实表达

- 连接条：live/connecting/syncing/degraded（无实时流时 HTTP 轮询兜底）/error
- 执行机离线：列表灰化 + 探测失败显式提示（不静默）
- 导入降级：模型被归一/降级时显式 warning（「已改用 XX 模型，建议先切换」），不静默跳进去一发 unanswered（P0-5）

## 8. 执行机与跨机

- **接入**：hub 出站 SSH（机器零安装常驻进程，比 connector 轻）；探测 5s 超时，30s 节流缓存
- **在线状态**：/api/executors 秒回（缓存 + 后台刷新）；离线执行机在新建弹窗禁选
- **迁移语义**：工作区文件级搬运（harvest 从会话历史挖 read/write/edit 清单 → 中转 → 校准提示）。重于 sig 的 handoff brief（指针），因为我们搬的是真实文件——这是差异化能力
- **失联语义（P1-1 规划，未实施）**：执行机断线时其上运行中会话标「失联」（amber，不红）；断线期间 steer 排队，重连后投递 + 对账（还在跑→继续；已结束→拉快照）。需要 server 侧 per-env 会话状态机

## 9. 持久与恢复

三层（对齐 sig §1.6 的分层框架，我们的实现）：

1. **协议层**：requestId 幂等（重复提交不双跑）；WS 断线 30s 内重连 + snapshot 全量对账；事件扇出去重（attach 竞态修复 b472d22）
2. **进程层**：hub 崩溃 → systemd 拉起 → pi-durable 从 SQLite 恢复全部会话（M1 验证过 SIGKILL 演练）；执行机侧无常驻状态（SSH 按需连接），机器重启只是「离线」不是「损坏」
3. **语义层**：无人 attach 时幽灵流仍跟踪事件（run_end 自停、有人看时交棒）——保证 status/unread/收尾卡不因「没人看」而失真（10-28 修复）

**pi 导入链路**（我们和 sig 最大的场景差异——它不做导入，我们以此为高频入口）：导入 ≠ 成功，模型渠道兼容性归一 + 冒烟 warning（P0-5）是第一道关；**场景级回归测试是欠账**（10-26 四连 bug 的根因，见 §14 开放问题）。

## 10. 并发与隔离

- 当前 single-player：无隔离需求
- 多用户方案已想清楚未实施（owner 字段 + Tailscale-User-Login 头 + BYOK 渠道，见 roadmap §1）——本文档不展开，实施前先回来改 §2/§4
- 会话级并发：同一会话流管理串行化（opChains per-conv promise 链）；多设备同时 attach 同会话 = 多观察者（快照 + 事件流双投递）

## 11. 入门、安全与成本

### 11.1 入门流程

零会话空态 → 两步指引（新建选执行机 / 导入 pi 会话）→ 首条消息 → 自动命名/分组。缺渠道 key/执行机全离线的 setup banner 状态机是欠账（参考分析 §4.1 尾部，未排期）。

### 11.2 安全

私网（Tailscale）+ serve TLS；guard 确认流（fail-closed）；审计日志（audit.jsonl，5MB 轮转）；模型 key 环境变量注入不落库。多用户后加：执行机归属校验、tailnet ACL 收紧（roadmap §1）。

### 11.3 成本透明（P1-3 规划，未实施）

当日 token 花费（pi usage 汇总、per-day 聚合）在设置「关于」页展示。开源前的信任基建：自托管者必须能回答「这东西今天花了多少钱」。

## 12. 能力边界（明确不做）

| 不做 | 理由 |
|---|---|
| 管家式 LLM 调度层 | sig 的核心，但与驾驶舱心智冲突；我们的人直接驾驶 |
| 记忆模块（容量驱逐/两阶段写入） | pi-durable 持久层已覆盖；上下文治理走 compaction（roadmap） |
| 多租户 SaaS | 永远不做（产品真相拍板） |
| 云沙箱执行 | 工具在用户电脑上跑是原则 4 |
| UI 组件库 / 手动深色切换 | ADR-010 / 深色自动跟随是硬约束 |
| 手机设置入口 | 驾驶舱克制（P0-4 显式例外：只读的「等你」聚合可以） |

## 14. 开放问题

1. **导入链路场景测试**：从真实 pi 会话文件抽样建回归（覆盖 envId/渠道名/thinkingLevel/双写四类坑）——sig 的 crash-recovery.test.ts 路线，未排期
2. **compaction**：长会话上下文治理（只增不删的代价何时到临界）
3. **失联语义的状态机归属**：per-env 还是 per-conv（P1-1 实施时定）
4. **「等你」是否扩展**：未答问题（agent 的 ask）现在不算 pendingConfirms，要不要并入聚合（sig 的 Needs you 含两者）
5. **多用户实施时机**：同事接入需求出现时回来改 §2/§4/§10
